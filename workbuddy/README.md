# 文档漂移侦探（doc-drift-expert）

**代码天天在改，文档却停在过去。** 类删了文档还在写、接口改了说明没跟上、需求在群里变了却没人记——新人照着文档走弯路，AI 助手读着过时的 AGENTS.md / CLAUDE.md 写出错代码。

文档漂移侦探帮你把这些"漂移"找出来，问清以谁为准，再把文档修好。

## 它能找出什么

| 问题 | 例子 |
|---|---|
| 过时引用 | 文档写着 `PricingRuleExecutor` 负责定价，但这个类半年前就删了（用 git 历史证明） |
| 说已删除却还在 | 文档说"`TeamController` 已下线"，代码里还在用 |
| 链接坏了 / 路径写错 | 链接写成了同事电脑上的 `E:/workFile/...`，给出可直接替换的相对路径 |
| 内容可能过时 | 文档最后更新之后，它描述的代码又改了 5 次，逐条判断描述还准不准 |
| 没有文档的接口 | 有 10 个接口的 Controller，任何文档都没提到 |

**AI 规则文件优先**：AGENTS.md、CLAUDE.md、.cursorrules 每次对话都会被 AI 读到，过时的危害最大，排在最前。研究发现约 23% 的开源仓库里，这类文件引用了已不存在的代码。

## 它怎么干活

1. **认识项目**：盘点所有文档，分清哪些是"现状说明"、哪些是"某次迭代的历史记录"（历史记录不要求跟代码同步，不会被误报）。拿不准的按目录一次问你。
2. **体检**：规则 + git 历史做确定性检查，秒级出结果；再逐节判断"代码改了之后文档还准不准"。报告写在项目的 `.doc-drift/reports/` 里。
3. **修文档**：按文档分组给出"改哪几处、为什么、改成什么"，你确认后才动手；改完再体检一遍确认消掉。
4. **记结论**：你回答过的问题记在 `.doc-drift/answers.md`，下次不再问。

只改文档，不擅自改业务代码。

## 使用要求

- 项目是 git 仓库（用 git 历史判断"以前有过、现在没了"）。
- Node ≥ 18.17（没有的话自动用 WorkBuddy 自带的 Node）。
- 可选：StartLux 密钥（`DOC_DRIFT_API_KEY` 或 `BAMBOO_API_KEY`）。配置后文档分类和"是否过时"由 StartLux 判断，更快更省；不配置时由专家自己判断。

## 隐私

- 检查在本机进行，只读你的代码，只在项目里写 `.doc-drift/` 目录。
- 不配置 StartLux 时，不会把内容发给 WorkBuddy 之外的任何服务。
- 配置 StartLux 时，会把被判断的文档片段与相关代码改动发给 StartLux（已过滤密钥、token、密码等常见写法）。

## 实测

在一个 Java 后端项目（1668 个 Java 文件、186 篇文档）上：全量规则检查不到 2 秒；CLAUDE.md 里找出 10 处过时引用，全部属实（已删除的定价引擎、规则执行器、第三方对接、测试类）；28 处错误路径的链接给出了可直接替换的相对路径。

## 最适合

- 文档多、迭代快、多人维护的业务系统（尤其 Java / Spring 项目，接口与表名识别最完整）；
- 用 AI 编程助手、维护着 AGENTS.md / CLAUDE.md 的团队；
- 接手老项目、要先弄清"哪些文档还能信"的人。
