# 文档漂移侦探（doc-drift-expert）

**代码天天在改，文档却停在过去。** 类删了文档还在写、接口改了说明没跟上、需求变了文档没跟着改——新人照着文档走弯路，AI 助手读着过时的 AGENTS.md / CLAUDE.md 写出错代码。

文档漂移侦探帮你把这些"漂移"找出来，问清以谁为准，再把文档修好。

## 它能找出什么

| 问题 | 例子 |
|---|---|
| 过时引用 | 文档写着 `PricingRuleExecutor` 负责定价，但这个类半年前就删了（用 git 历史证明） |
| 说已删除却还在 | 文档说"`TeamController` 已下线"，代码里还在用 |
| 链接坏了 / 路径写错 | 链接写成了同事电脑上的 `E:/workFile/...`，给出可直接替换的相对路径 |
| 文档和现在的代码对不上 | 文档这一节说"价格乘 10"，代码现在是乘 20；逐节判"过时 / 准确 / 看不出"，并给方向：改文档、改代码、两边都改、拿不准 |
| 改了代码、文档没跟上 | 这一轮改到的代码，牵动了哪几篇文档的哪几个小节（本地算，不调模型，先问你要不要核对） |
| 没有文档的接口 | 有 10 个接口的 Controller，任何文档都没提到 |

**AI 规则文件优先**：AGENTS.md、CLAUDE.md、.cursorrules 每次对话都会被 AI 读到，过时的危害最大，排在最前。研究发现约 23% 的开源仓库里，这类文件引用了已不存在的代码。

## 它怎么干活

1. **认识项目**：盘点需求 / 设计 / SPEC 文档和代码，建立"文档 ↔ 代码"对应关系；如果项目用 Trellis，还会记下活跃任务和当前 SPEC，体检默认只查当前任务那几篇。默认一律以当前代码为准，不用你先给文档定状态。
2. **体检**：规则 + git 历史做确定性检查，秒级出结果；再逐节拿文档**现在的说法**和代码**现在的实现**比（不看谁比谁新，提交了也能重算）。`doctor` 默认当前 SPEC，`doctor full` 查所有活跃任务 + AI 规则文件。报告写在项目的 `.doc-drift/reports/` 里。
3. **日常钩子**：每轮结束只看这一轮改到的代码，本地算出可能过时的文档小节——**不调模型**，先问你要不要核对；你说要才跑一次 `check`。平时不打扰，也不花钱。
4. **问你、再同步文档**：核实后真正不一致的地方，用选择题问你（以代码为准改文档 / 文档才对、代码有问题 / 我来说明），一次最多 4 题；按你的选择把文档同步到当前代码，改完再体检一遍确认消掉。
5. **记结论**：你回答过的问题记在 `.doc-drift/answers.md`，下次不再问；说"先记下来"的进 deferred，不重复打扰。

**只同步文档，不改代码。** 以当前代码为准；你判断"文档才对、代码有问题"的地方，记进 `.doc-drift/code-todo.md`（代码待改清单），交给你们自己的改代码流程。

## 使用要求

- 项目是 git 仓库（用 git 历史判断"以前有过、现在没了"）。
- Node ≥ 18.17（没有的话自动用 WorkBuddy 自带的 Node）。
- 可选：StartLux 密钥。到 [bamboonode.dev](https://bamboonode.dev/) **免费注册**即可领取，设置成环境变量 `DOC_DRIFT_API_KEY`（或写进 `~/.doc-drift/.env`：`DOC_DRIFT_API_KEY=你的密钥`）。配置后文档分类和"是否过时"由 StartLux 判断，更快更省；不配置时由专家自己判断，功能一样能用。

## 隐私

- 检查在本机进行，只读你的代码，只在项目里写 `.doc-drift/` 目录。
- 钩子本身不发任何请求；只有你确认后的 `check` 和手动 `doctor` 才把被判断的文档片段与相关代码发给 StartLux。
- 发出前过滤密钥、token、密码等常见写法。

## 实测

在一个真实项目上：`doctor full --no-model` 2.4 秒，只查活跃任务的 SPEC 文档；钩子 pre-step 218 ms、turn-stopping 205 ms；没有候选时完全不说话。旧版"每轮判需求"实测 97 次模型请求里 93 次什么也没产出（96% 浪费），所以改成"用户确认后才查"。

## 最适合

- 文档多、迭代快、多人维护的业务系统（尤其 Java / Spring 项目，接口与表名识别最完整）；
- 用 AI 编程助手、维护着 AGENTS.md / CLAUDE.md 的团队；
- 用 Trellis 管任务、希望文档跟着任务收口的团队；
- 接手老项目、要先弄清"哪些文档还能信"的人。
