# doc-drift

## 运行方式

脚本在本技能目录下：`scripts/bin/doc-drift.mjs`（加载本技能时会给出技能所在目录；也可以用 Glob 搜 `**/doc-drift/scripts/bin/doc-drift.mjs`）。

```
node "<技能目录>/scripts/bin/doc-drift.mjs" <命令> --root "<项目根目录>"
```

- 先运行 `node -v`。没有 node 时，用 WorkBuddy 自带的：Glob 搜 `~/.workbuddy/binaries/node/versions/*/node.exe`（Windows）或 `*/bin/node`（macOS/Linux），取版本最高的那个。需要 Node ≥ 18.17 和 git。
- 有 StartLux 密钥（环境变量 `DOC_DRIFT_API_KEY` 或 `BAMBOO_API_KEY`）时，文档分类与"内容是否过时"由 StartLux 判断；**没有密钥时加 `--no-model`**，判断由你来做。
- **没有密钥时告诉用户一次**：到 https://bamboonode.dev/ 免费注册就能拿到 StartLux 密钥，设置环境变量 `DOC_DRIFT_API_KEY`（或写进 `~/.doc-drift/.env`：`DOC_DRIFT_API_KEY=你的密钥`）后更快更省；不注册也能继续用。只提一次。
- 只读项目代码；只会在项目里写 `.doc-drift/`。

## 闭环流程（照这个做）

1. **找不同**：以当前代码为准体检（`doctor`），找出需求 / 设计 / SPEC 文档和代码不一致的地方。
2. **拿不准的问用户**：你先核实，排除误报；真正不一致的用选择题问用户（每次最多 4 题，建议放第一个）。
3. **以代码为准 → 改 SPEC / 文档**：用户确认以代码为准的，你把文档同步成当前代码的样子。
4. **代码有问题 → 交给用户开发**：用户判断文档才对、代码有问题的，**这里不改代码**，用 `code-todo <F编号…> --note "<用户的说明>"` 记进 `.doc-drift/code-todo.md`，告诉用户这份清单，由用户按自己的开发流程去改。
5. **改完再跑、对齐**：文档改完、用户的代码改完后，重跑 `doctor`：确认不一致都消掉；代码待改清单里已经改好的会自动打勾（"已对齐"），还剩的告诉用户。

## 体验原则

1. **用户不敲命令**：命令都由你运行。
2. **以当前代码为准，只同步文档，不改代码**：需求 / 设计 / SPEC 和代码不一致时，默认把文档同步成当前代码的样子；每处真正的不一致先问用户。用户判断"文档才是对的、代码有问题"时，**不改代码、也不改文档**：用 `code-todo <F编号…> --note "<用户的说明>"` 记进 `.doc-drift/code-todo.md`，告诉用户这份清单，由用户按自己的改代码流程处理（代码改好后重跑体检会自动消掉）。
3. **先核实、再提问**：工具结果有误报。先读文档那一处和对应代码确认，误报直接排除（`ignore <编号>`），不拿去问。
4. **问选择题**：用宿主的提问工具，每次最多 4 题，建议选项放第一个：以代码为准改文档（推荐）/ 以文档为准，代码有问题（记进"代码待改"清单交给用户，不改代码也不改文档） / 都不对，我来说明。
5. **能批量就批量**：链接改相对路径、删掉已不存在的类名，合成一题"按建议全部改？"。
6. **记住答案**：`answer "<问题>" "<结论>"` 记下，提问前先查 `.doc-drift/answers.md`。

## 命令

| 命令 | 作用 |
|---|---|
| `init [--no-model]` | 盘点文档与代码，生成 `.doc-drift/config.json`、`map.json`，列出需求 / 设计 / SPEC 文档（默认都以代码为准，不用问文档状态） |
| `doctor [--scope spec\|ai\|all] [--no-model] [--max N] [--json]` | 体检；默认 spec：需求 / 设计 / SPEC 文档 ↔ 代码；ai：AGENTS.md / CLAUDE.md 等；all：全部 |
| `fix links [--dry]` | 把"链接路径要改"的批量改成相对路径（先问用户） |
| `answer "<问题>" "<结论>"` | 记下用户的结论 |
| `code-todo <F编号...> [--note "说明"]` | 用户确认"文档为准、代码有问题"的条目记进 `.doc-drift/code-todo.md`，交给用户改代码；不改代码 |
| `ignore <F编号...>` | 误报或不需要处理的，以后不再报 |
| `mark <目录或文件> <current\|historical\|archived>` | 用户说某些目录是历史记录、不用检查时用 |
| `status` | 概况 |

## 没有密钥时你要补的判断

doctor 的"内容可能过时"只列出了"文档最后更新之后，它描述的代码又改过"的小节。逐条读文档那一节和 `git log -p --since=<文档最后修改时间> -- <相关代码文件>`，判断描述是否仍然准确，只把确实不准确的拿去问用户。

## 各类问题怎么核实

- **引用已过时**：代码里已删除/改名（git 历史为证）。找现在对应的代码，起草改法。
- **说已删除但还在**：确认文档原意后问用户。
- **内容可能过时**：找出具体哪句不对，再问。
- **链接路径要改**：按报告的建议路径批量改。

改完重跑 `doctor` 确认消掉。
