# 开发 SOP（通用 / BladeX 两套）

一套跨项目的开发流程：任务有状态、开工前先反讲、实现和验收分开、文档漂移有人管。
**通用版不需要 BladeX**，家里、个人项目、非 Java 仓库都能直接照抄；BladeX 项目只在技能映射上换一列。

---

## 0. 适用范围

| 版本 | 用什么 | 适合 |
|---|---|---|
| 通用版（默认） | `grilling`（/grill-me）逼需求 + `tdd` + `code-review` + `feynman-analysis` + `ponytail` + `ub-mode` | 任意仓库；没有 BladeX、没有 Trellis 也能跑 |
| BladeX 版 | 通用版的流程不变，技能换成 `blade-audit` / `blade-doc` / `blade-design` / `huashu-chrome` | 基于 BladeX 的 Java 后端项目 |

流程本身与语言、框架无关；**换的只是每个角色手里那把工具**。

---

## 1. 状态源

- 有 Trellis：`.trellis/` 是唯一任务状态源，任务建在 `.trellis/tasks/<日期>-<名字>/`，必须有 `prd.md`、`MILESTONES.md`，用官方 `task.py` 建/启动/收口/归档。
- 没有 Trellis：用一个 `tasks/<日期>-<名字>/` 目录代替，至少留 `prd.md` 和 `MILESTONES.md`，状态写进 `task.json` 或 issue。
- **不要同时维护两套状态**（Blade Spec、Comet、Matt 的 to-spec/implement 都会另立状态，禁用）。

`MILESTONES.md` 记四类东西：谁在什么时候做了什么、关键决定和理由、验证证据（命令 + 结果）、未完成项。**由 Lead 记录**，实现/测试角色不写任务日志。

---

## 2. 流程

```
需求 → 记录任务 → 派活 → 费曼反讲 → Lead 确认 → 实现 → 独立验收 →（可选评审）→ 收口 → 归档
```

| # | 步骤 | 谁 | 产出 / 门禁 |
|---|---|---|---|
| 1 | 需求澄清 | Lead | 用 `grilling` 把目标、边界、非目标问清楚；有歧义先问，不猜 |
| 2 | 记录任务 | Lead | `prd.md`：背景、验收标准、文件边界；建任务并启动 |
| 3 | 派活 | Lead | 给每个角色一份自包含 brief：目标、允许改的路径、禁止碰的路径、验收怎么证明 |
| 4 | 费曼反讲 | Developer / Tester | 各讲一遍：为什么做、输入→处理→输出、改哪些文件、每条验收怎么证明、不确定点 |
| 5 | 确认开工 | Lead | 明确回「确认开工」；反讲有错就重讲，不辩论绕过。**确认前不写代码、不跑测试** |
| 6 | 实现 | Developer | 只改 brief 里的范围；先想最小改法（`ponytail`）；按 `ub-mode` 先跑通再改对；非平凡逻辑留一个小测试 |
| 7 | 独立验收 | Tester | 用同一份验收标准复跑，给可复现证据；开发者自测不算数 |
| 8 | 评审（可选） | Lead / `code-review` | 只看实际 diff + 证据；失败退回 Developer，Tester 按原标准复验 |
| 9 | 收口 | Lead | 问用户要不要跑文档检查；把结论写进 `MILESTONES.md`；任务完成才归档 |

**硬门禁只有两个**：反讲没确认不开工；测试没独立复验不算过。

---

## 3. 验收标准怎么写

验收写不实，流程就是空转。每条必须满足：

1. **可执行**：给出确切命令或唯一短语，不用「功能正常」这种话。
2. **有区分度**：改之前必须不成立、改之后成立。先想一遍「现在跑这条会不会已经通过」。
3. **覆盖边界**：正常路径 + 一个失败路径 + 一个不该变的相邻行为。
4. **未跟踪文件**（Harness 配置、生成物）：用「改前 SHA256 + 限定路径的 `git status --short` 差量」，不要写「git status 干净」——仓库本来就可能有一堆未跟踪文件。
5. **证据可复现**：命令、退出码、关键输出行，写进 `MILESTONES.md`。

## 4. 角色 × 技能

| 角色 | 职责 | 通用版 | BladeX 版 |
|---|---|---|---|
| Lead | 收需求、拆任务、定边界、终审 | `grilling`、`code-review`、`feynman-analysis`（审反讲） | `blade-audit`、`blade-doc` |
| Developer | 只实现已确认任务 | `tdd`、`ponytail`、`ub-mode`、`feynman-analysis` | `blade-doc`、`blade-design`（脚手架由 Lead 先批） |
| Tester | 只测试、给证据 | `feynman-analysis`、浏览器类技能按需 | `blade-audit`、`huashu-chrome` |
| Codegen（可选） | 标准 DDL/CRUD 骨架 | —（通用项目通常不需要） | `blade-design` |
| 文档 | 文档↔代码一致性 | `doc-drift` | `doc-drift` |

搜索：有代码图谱先查图谱（如 `codegraph explore "问题"`），没有再查项目索引 + 定向 grep/read，**禁止全库盲扫**。

模式选择（不改变流程和门禁）：`ponytail` 管「少写代码」——能删就删、能复用就复用；`ub-mode` 管「实现节奏」——先跑通（First Make it Work）→ 再改对（Make it Right）→ 再按规范（Follow Practice），适合新功能和重构。两个可以同时开。

## 5. 文档漂移（doc-drift）

- 钩子每轮只做本地记账；**一轮结束由钩子本地判断要不要问你**——这轮改动关联到需求/设计文档才发一句话，没关联就不打扰。
- 你同意才跑 `doc-drift check`（只核对刚才那批候选）；`doc-drift doctor` 只有你要求才跑。
- 判断口径是「文档现在的说法 vs 代码现在的实现」，不依赖 git diff。
- 每条冲突先问用户以哪边为准（可能需求改了、文档没跟上）；用户确认后才改文档。
- 任务收口时**先问用户要不要跑 doctor，同意才跑**，结论写进 `MILESTONES.md`。

---

## 6. 收口清单

- [ ] `prd.md` 的验收标准都执行过，证据在 `MILESTONES.md`
- [ ] 独立 Tester 复验通过（不是开发者自测）
- [ ] Lead 看过实际 diff，不只看测试结论
- [ ] 问过用户要不要跑 `doc-drift doctor`；跑了就记结论
- [ ] 未完成项如实保留；确实完成才归档
- [ ] 提交/推送/PR/部署只在用户明确要求时做

---

## 7. 已知坑

| 坑 | 处理 |
|---|---|
| 验收写「git status 干净」 | 未跟踪文件会让它永远失败；改用改前 SHA256 + 限定路径差量 |
| 多角色抢写 `MILESTONES.md` | 定为 Lead 独占写 |
| 子代理没有父会话的任务指针 | 跑文档检查时显式带 `--task <任务目录名>` |
| 同一天两种 doctor 报告互相覆盖 | 报告按 `日期-task-<任务名>.md` / `日期-full.md` 分开命名 |
| 反讲讲太长 | 固定五问，一段话讲完；讲不清就是没想清 |
| 门禁靠自觉 | 目前是软约束；不为了强制它去改 hook 或任务状态机，成本大于收益 |

## 8. 最小任务模板

```markdown
# <任务名>

## 背景
一句话说明为什么要做。

## 范围
- 允许改：<路径>
- 禁止碰：<路径>

## 验收标准
1. <命令> → <期望输出/退出码>
2. <唯一短语> 出现在 <文件:行>
3. 相邻行为 <X> 不变

## 未完成（收口时填）
- 
```
